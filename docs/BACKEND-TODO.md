# 프론트엔드 연결을 위해 백엔드에서 할 일

## 현재 상태와 분석 기준

마지막으로 첨부된 서버·앱·웹 ZIP은 이전 검토 파일과 바이트 단위로 같습니다. 현재 소스 분석 기준은 아래와 같습니다.

| 파일                       | SHA-256                                                            |
| -------------------------- | ------------------------------------------------------------------ |
| RoutineSlim-Server-dev.zip | `6c5d5c13ab4a35f43eec2b003ac93161a3f2e9e965a1b3637a6fb86ec9200784` |
| RoutineSlim-App-dev.zip    | `07d9ce19e6eb4fd9b19f43330ddac016a34e3836123a37dc9d56014d53771473` |
| frontend.zip               | `4ebe0a119391208f424deab452e46dd34a15f2c2a9beb427ba9cd05aa4bd624a` |

이 서버 ZIP에는 JWT 발급·검증 구현이 없고, 로그인은 회원 UUID를 반환합니다. 앱의 로그인 라우트는 서버 인증 없이 홈으로 이동하며 주요 화면은 샘플 데이터를 사용합니다. **앱·웹·서버 정보 공유가 완료된 상태가 아닙니다.** 대화에서 언급된 `feat/auth-jwt` 머지 버전과 실제 배포 서버가 이 ZIP과 같은지는 별도 확인이 필요합니다.

프론트의 일반 로그인·구독 요청 변환은 준비돼 있지만, 실제 서버/DB 통합은 검증하지 않았습니다. 프론트 테스트의 모의 응답을 서버 기능 구현으로 간주하면 안 됩니다.

## 서버 실행 선행 조건

- 현재 첨부 `build.gradle`은 Java 21과 Spring Boot 4.1.1을 지정합니다. 이전 IntelliJ 예제의 Java 17 설정과 혼동하지 마세요.
- 배포 프로필은 `SPRING_PROFILES_ACTIVE=prod`이며 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 서버 실행 환경에 설정합니다. 비밀번호를 프론트 `.env`나 소스에 넣지 않습니다.
- DB_URL의 호스트·포트·스키마는 팀에서 확정한 값을 사용합니다. 대화에서 변경한 `routineslim_server` 스키마가 실제 서버 설정에도 반영됐는지 확인합니다.
- MySQL 연결과 Flyway 마이그레이션이 완료되고 JPA validate를 통과해 Spring이 실제로 시작되는지 확인합니다.
- 서버 8080은 그대로 둡니다. DB 포트와 HTTP API 포트는 서로 다른 설정입니다.

## 1순위: 주소·인증·기본 데이터 규격 확정

### 1. 기존 8080에서 화면과 API 함께 제공

- 서버 주소/포트 `http://localhost:8080`을 유지합니다.
- 프론트 `dist` 내용을 Spring의 `src/main/resources/static/`에 배치합니다.
- `/`, `/index.html`, `/assets/**`, `/fonts/**` 정적 경로를 로그인 전에도 열 수 있게 설정합니다.
- 회원·구독 데이터 API의 인증은 계속 적용합니다. 정적 화면 공개와 전체 API 공개는 별개입니다.
- 배치 후 `/`가 HTML, JS/CSS가 올바른 MIME 타입으로 반환되는지 확인합니다.
- 개발용 5173 프록시 설정은 정적 배포에 포함되지 않습니다. 같은 8080에서 배포하면 상대 경로 API를 사용합니다.

### 2. 앱·웹의 인증 계약을 하나로 맞추기

현재 첨부 서버는 `/auth/login`의 UUID 반환과 `.anyRequest().authenticated()` 사이에 인증 연결이 없습니다. `X-Member-Id`만 전달한다고 Spring Security의 인증이 자동으로 생성되지는 않습니다.

- 실제 적용할 방식이 현재 UUID 계약인지, 머지된 JWT 계약인지 확정합니다.
- JWT를 사용할 경우 실제 로그인·재발급·로그아웃 URL, 요청/응답 필드, 만료 시간, 토큰 전달 방식을 Swagger/OpenAPI 또는 예제 JSON으로 공유합니다.
- 서버 필터가 토큰을 검증하고 인증된 회원을 `SecurityContext`/Principal에 연결해야 합니다.
- 소유 회원은 검증된 인증 정보로 식별합니다. 요청의 회원 UUID만 신뢰해 다른 사용자의 데이터를 읽거나 수정할 수 있게 만들면 안 됩니다.
- 로그인 확인/현재 회원 API를 제공하고, 잘못되거나 만료된 인증은 401, 권한 부족은 403으로 구분합니다.
- JWT 버전이면 현재 UUID 기반 프론트 어댑터도 실제 계약에 맞춰 수정해야 합니다. 서버 변경만으로 자동 호환되지는 않습니다.
- `/api/csrf`는 현재 기본 `server-dev` 모드에서 사용하지 않습니다. 기존 쿠키/세션 서버 모드를 선택할 때만 해당 계약에 맞는 CSRF가 필요합니다.

회원가입·소셜 로그인·아이디/비밀번호 복구는 사용자의 요청에 따라 웹에서 제거했습니다. **이 절차를 이번 웹 연결의 필수 작업으로 다시 추가하지 않습니다.** 기존 계정의 비밀번호 변경·프로필 수정은 현재 로그인 후 마이페이지 기능으로 별도 범위입니다.

### 3. 공통 데이터 규격

- 회원/구독 UUID는 문자열로 앱과 웹에 동일하게 반환합니다. 카테고리·프리셋·카드의 숫자 ID와 구별합니다.
- 앱과 웹이 같은 계정과 같은 서버 DB를 사용하도록 연결합니다. 각 기기의 샘플 데이터·localStorage를 공유 DB처럼 취급하지 않습니다.
- 카테고리·프리셋의 실제 ID와 표시 이름을 조회할 API를 제공하면 수동 `.env` ID 매핑을 줄일 수 있습니다.
- 날짜는 `YYYY-MM-DD`, 월은 `YYYY-MM`, 서버 일정 기준은 합의한 `Asia/Seoul`로 통일합니다.
- 현재 웹의 금액 표시는 원화 기준입니다. 금액은 음수 없는 정수이고 Java int 범위와 프론트 검증 범위를 맞춥니다.
- 빈 목록은 `[]`, 알 수 없는 값과 조회 실패는 실제 0원/0건과 구분합니다.
- 오류 응답은 최소 `{ "message": "사용자가 이해할 수 있는 설명", "code": "분기용 코드" }`처럼 일관되게 제공합니다.

## 2순위: 로그인 후 첫 화면과 구독 관리

아래는 **현재 웹 화면/기능 API가 사용하는 계약**입니다. 앱·서버의 정식 경로를 다르게 정하면 프론트 기능 API/어댑터에 그 매핑을 추가해야 합니다.

| 기능                      | 현재 웹에서 사용하는 요청                            | 백엔드 작업                                                             |
| ------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------- |
| 현재 로그인 확인          | `GET /api/me`                                        | 현재는 브라우저 UUID 복원만 함. 서버 검증 기반 현재 회원 조회 계약 필요 |
| 일반 로그인               | `POST /api/login` → 기본 어댑터의 `POST /auth/login` | 실제 JWT/UUID 응답 계약 확정                                            |
| 로그아웃                  | `POST /api/logout`                                   | 현재 UUID 모드는 브라우저 정보만 삭제. JWT면 서버 토큰 폐기 정책 연결   |
| 구독 목록/등록            | `GET/POST /api/v1/subscriptions`                     | 인증 회원의 데이터만 조회·저장                                          |
| 구독 상세/수정/삭제       | `GET/PUT/DELETE /api/v1/subscriptions/{id}`          | 소유권·필수 필드·금액·주기 검증                                         |
| 구독 상태                 | `PATCH /api/v1/subscriptions/{id}/status`            | ACTIVE/TRIAL/PAUSED/CANCELED의 의미 유지                                |
| 카테고리/빠른 서비스 선택 | 웹 `GET /api/v1/catalog`                             | 카테고리·프리셋 데이터 제공 또는 정식 category/preset API와 매핑        |
| 월/연 예상 구독료         | `GET /api/v1/expenses/summary`                       | 월 환산·활성 구독 개수·카테고리별 합계                                  |
| 절약 검토 요약            | `GET /api/v1/savings/summary`                        | 검토 표시 기반 예상액 계산                                              |
| 월간 실제 지출            | `GET /api/v1/reports/monthly?month=YYYY-MM`          | 실제 결제 기록 합계·이전 월·6개월 추이                                  |
| 결제 예정                 | `GET /api/v1/reminders`                              | 구독의 다음 결제 일정과 D-day                                           |

기존 서버에 있는 구독 컨트롤러도 인증·소유권 연결을 통과하는 실제 요청으로 검증해야 합니다. 코드에 엔드포인트가 있는 것과 실제 호출 성공은 다릅니다.

### 구독 모델에서 합의할 차이

- 웹 `category`, `cycle`, `day`, `billingAnchorDate`와 서버 `categoryId`, `billingCycle`, `billingDay`, `startDate`의 대응을 확정합니다.
- 현재 어댑터는 ACTIVE 구독과 월/주/연의 일부 편집만 지원합니다. 앱 화면의 지원 주기와 서버의 `cycleInterval`도 확인해야 합니다.
- 웹의 `review`는 "절약 검토" 표시입니다. 서버의 PAUSED/CANCELED로 바꾸면 실제 의미가 달라집니다. 검토 전용 필드/API를 추가하거나 별도 모델을 합의합니다.
- 서버는 startDate에서 billingDay를 계산하고 웹은 두 입력이 분리돼 있습니다. 단일 기준일 정책 또는 독립 결제일 정책을 확정합니다.
- 기존 카드·알림·메모 필드가 웹 전체 수정 요청으로 사라지지 않도록 PUT 정책을 명확히 합니다. 현재 어댑터는 기존 값을 먼저 읽어 보존합니다.

### 요약 응답 예시

다음은 현재 웹이 소비하는 형태의 예시이며 실제 운영 데이터가 아닙니다.

```json
{
  "monthlyTotal": 27900,
  "annualTotal": 334800,
  "subscriptionCount": 2,
  "byCategory": { "영상": 17000, "음악": 10900 }
}
```

월간 실제 지출은 `total`, `previousTotal`, `hasPrevious`, `difference`, `paymentCount`, `categories: [{category, amount}]`, `history: [{month, amount}]`를 사용합니다. **history 필드는 total이 아니라 amount**입니다. 예상 구독료와 실제 결제 내역을 같은 숫자로 대신하지 않습니다.

## 앱·웹 정보 공유의 완료 조건

1. 같은 사용자로 앱과 웹에서 실제 로그인합니다.
2. 앱에서 저장한 구독 UUID와 필드를 웹 재조회에서 확인합니다.
3. 웹 수정 내용이 앱의 재조회/화면 복귀 후 반영되는지 확인합니다.
4. 다른 계정에서는 그 구독을 조회·수정·삭제할 수 없어야 합니다.
5. 새로고침·재로그인·토큰 만료·잘못된 토큰에서도 계정이 섞이지 않아야 합니다.
6. 날짜·금액·카테고리·상태가 양쪽에서 같은 의미로 표시돼야 합니다.

현재 앱의 샘플 목록과 로그인 우회는 앱 담당자가 실제 서버 호출로 연결해야 합니다. 웹의 공통 통신 모듈과 DTO 타입은 이 연결에 사용할 수 있지만, 앱 소스에 적용하거나 실기기 검증을 완료한 것은 아닙니다.

## 프론트에서 함께 해야 할 작업

현재 기본 `serverApiAdapter.js`는 기존 첨부 서버의 로그인/구독 일부만 허용합니다. **서버에 새 API를 추가해도 현재 프론트가 자동으로 모든 기능을 호출하지는 않습니다.** 다음을 함께 진행해야 합니다.

- 실제 JWT 계약에 맞춰 `global/api/apiClient.js`/`global/api/routineSlimApiClient.js`의 인증 헤더·재발급을 조정합니다.
- 구현된 기능은 `src/domain/{기능}/*Api.js`와 어댑터에 경로·응답 매핑을 연결합니다.
- 기본 응답을 가짜 성공/빈 목록으로 대체하지 않고 실제 데이터로 검증합니다.
- 조회 실패·지원 안 됨·정상 빈 목록을 구분합니다. 현재 웹은 부분 조회 실패 시 읽힌 구독을 보여주고 알 수 없는 집계는 —로 표시합니다.
